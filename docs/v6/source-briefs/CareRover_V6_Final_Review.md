## 02｜五项交付，一条展示主线

影片、网页、自由探索、操作台和实体包不能各自发展成不同版本。

| 产物 | 用户怎样用 | 完成标准 |
|---|---|---|
| 发布影片 | 一次点击或本地播放器，自动播放 | 约 150 秒完整 MP4，含移动、手势、健康和控制台；无手动滚屏依赖 |
| 产品网站 | 原生滚动参观，或逐页 Deck 讲解 | 同一内容/时刻可反向、跳转、暂停；资源离线可用 |
| 自由探索 | 完整进入，悬停/按钮展开，点选聚焦 | 真正 360°、上下方、缩放、布局清楚，退出返回原位置 |
| 操作台 | 看实时视频和状态，实际控制 | 数据来源、控制权限、命令目标、停止确认明确；不是宣传页套摇杆 |
| 同版实物包 | 现场识别设备、备份、构建、烧录、测量 | 实际两板、FFat、NVS/配置与记录一致；逐项放行，不能只靠版本名字 |

影片与产品展示绝不连接机器人。影片里出现控制台可以录真实 UI 的明确模拟会话，或采用有记录的真机会话；两者在画面内标清。打开操作台只导航，不能自动取得控制、切 MANUAL 或恢复旧速度。

最终要讲清同一条线：**它是什么 → 如何组成 → 怎么运动 → 如何理解手势 → 人怎样使用 → 如何实际操作 → 失效时怎样处理。**

## 04｜手势到底做了什么：按生产代码拍片

当前映射来自 `gesture_actions.h`，不是为影片随意设计一套手势。[S02]

| 检测标签 | 已有动作语义 | 影片与现场应怎样说 |
|---|---|---|
| LIKE | 启动跟随，但还要有合格新目标、权限与安全条件 | “做出手势，确认后进入跟随” |
| DISLIKE | 普通停止并清 owner | “停止当前动作”；**不是急停锁存** |
| TWO | 顺时针转动 | 方向以底盘俯视约定及实际测试为准，不拿自拍左右判断 |
| THREE | 逆时针转动 | 可作为另一方向示例，不必把每个别名都拍一遍 |
| OK | 与 THREE 同为逆时针动作入口 | 是别名，不虚构第六种能力 |
| PALM / FIVE 等其他可显示标签 | 此表中无对应动作 | 不演成挥手就停、张掌就后退 |

SAFE 的起动确认默认 4 个合格输入帧，DISLIKE 为 2 帧；DEMO 使用限定窗口内投票。动作框还要求宽度至少 80 像素，通常高度至少 120 像素，LIKE 为 110 像素；输入是 320×240 图像尺度下的门槛。主循环另检查动作分数、过滤后状态和非 held 条件。[S02][S05]

**四帧不等于固定四百毫秒。** 不为影片顺滑削掉确认帧。拍摄动作可经过剪辑，但不可宣传某个未经测得的识别延迟；需要精确值时记录现场输入帧、接受事件与目标变化时间。

### 手势显示、被允许、开始动作，必须分层

画面先显示 `检测到 TWO`，通过动作条件后才显示 `动作待确认/已受理`，设备模式/目标状态变化后才显示 `转动中`。真实物体已转完仍要实际观察，不能仅由 UI 定时器推断。

当前 WS 遥测主要包含 label/confidence/stable/held/age，没有动作请求的关联序号与接受/拒绝事件；`gesture_action` 是串口 JSON 输出。[S04] 所以不能看见 stable=true 就在操作台写“执行成功”。短期至少显示“识别结果”和“设备执行状态”两个独立字段；需添加动作事件时采用只读、有界的遥测扩展，并同步协议与模拟器，不能让浏览器替设备做动作裁决。

### OLED 不是从零开始

现有 `serviceOled()` 已把手势标签、置信度、心率/血氧的有效与保持状态、前方信息和 stopReason 送入 OLED UI。[S06] 虚拟屏幕应复用这些语义，但不等于真实固件已经会显示影片里新增的任意句子。拍真实 OLED 前先核对实际布局；影片的模拟屏和真实设备屏要分别验收。

## 05｜C01：为什么点了“手势控制”，动作可能反而不执行

**位置：** `safety_controller.h:85–115,141–155`；`wireless_runtime.cpp` 的 `wirelessGesture()`；网页 `changeMode()`。[S03][S04]

实际路径是：网页发送 `set_mode(GESTURE_CONTROL)` → 控制器把 owner 设为当前 client → 摄像头产生合格 TWO → runtime 调用 `autonomousTurn()` → 该函数发现 owner 非零 → 返回 `CONTROL_BUSY`。

本轮用已配置标定、在线网络、新鲜相机和 IMU 的合成输入直接调用生产控制器。SAFE/DEMO 都复现上述拒绝；LIKE 在有合格人物时也同样被拒绝。切到 IDLE 仍保留 owner，所以“先点待机再比手势”不是可靠的释放方案。[E02:GT09–GT11]

这不表示所有手势功能都坏了：无 owner 的自主入口可以启动；DISLIKE 的停止入口可以停止。但**“网页手势模式”与“自主手势模式”当前是两套不一致的准入语义**，现场非常容易误判成识别模型不行。

### 最小修复方向与今晚降级

不要删除 `CONTROL_BUSY`。应由团队选定唯一交接语义：如果现有网页的 GESTURE_CONTROL 就代表显式授权手势，应在控制器层允许该模式下、由当前已确认控制会话监督的合格动作，并让监督租约、失效停车、目标模式和所有权保持一致。手势 LIKE 转入 FOLLOW 也要延续或显式转换同一授权，不能偷偷归 owner=0。

这是已有功能的集成修复，但不只是换一个按钮：需要控制器/runtime/心跳/UI/测试一起验证。无法在冻结前完成，就把该路径从现场动作流程撤下，界面说明为“识别监视，未启用动作”，避免明知会拒绝还让演示者反复点击。

当前协议没有独立 release-control 命令；`control_allowed=true` 只意味着无人占有或当前 client 是 owner，不能区分二者。不要在网页凭这个布尔值写“已由我接管”。需要精确状态时再添加向后兼容的 owner/self 标识；未加就保留“当前允许请求/当前只读”。

### 不推荐的临时绕过

断开 owner 的 WebSocket 会停车并释放，但无 owner 的自主动作不因任意观察者 WebSocket 断开而停止。本轮也验证了这个区别。[E02:GT12–GT14] Wi-Fi station-disconnect 另有全局 stop 回调；本结论是控制器/WS 路径，不是所有网络失效的结论。不能把“断开网页才能动”作为用户友好的控制方案，更不能由此宣称存在持续监督。

## 06｜实时视频链路：三条数据不能混成一个“在线”

当前拓扑如下：[S07][S08][S09]

```text
CAM 摄像头板 ── MJPEG /stream ──────────────> 浏览器画面
     │                                      │
     └── UART 人脸/手势结果 ──> 主控 ── WS ───┤ 遥测/识别框/状态
                               ↑            │
                               └── cmd_vel / mode / estop ─ 浏览器
```

主控提供操作页面和 WebSocket；CAM 单独提供视频。它不是“主控把带识别框的完整视频放进 WS”。目前识别元数据与 JPEG 无共同逐帧标识，叠加应说明是异步识别反馈，不承诺每个框与当前 JPEG 精确同帧。

| UI 指标 | 真正来源 | 不能代替什么 |
|---|---|---|
| 控制连接/RTT | 主控 WS 与 ping/pong | 不能证明图像更新、实体已停止 |
| robot 状态年龄 | robot 子块最近时间 | 不能被 health-only 遥测续期 |
| 视频帧到达年龄 | 真正接收/解码成功的新 JPEG | 不能用 naturalWidth 或图像像素变化代替 |
| 人脸/手势年龄 | 各自 seq/age | 不能用通用 camera-online 续期 |
| AI FPS | CAM 结果流计数 | **不是视频 FPS**，P 与 G 频率也不同 |
| 指令目标 | 主控 target | 不是编码器轮速、不是里程计 |

当前地址配置中主控是 `192.168.4.1`，CAM 流为 `http://192.168.4.2/stream`；这只是源码配置，现场仍要核对实际设备。公网 HTTPS 页面不能靠放松 Origin 或拼接不安全 WS 代替同源设备控制台。展示页不需要访问这些地址。

## 07｜C02：画面“还在”不等于视频“还活着”

**位置：** `js/video.js:20–22,52–71`。当前 `load` 后 ready=true，绘制时只要 `naturalWidth>0` 且没有 error，就继续认为 ready。没有帧到达时间。[S07]

本轮用原生产文件、替身 DOM 与依赖注入一个已加载图像，不再发送任何帧事件，虚拟推进 60 秒并重复 render；它仍 ready，识别叠加仍被允许。显式 connection(false) 则正确变为不可用。这验证的是代码的判定边界，不是已复播一段真实冻结视频。[E03]

本地 HTTP 两帧后静默的浏览器试验因环境策略拒绝导航，保留 NOT RUN。CAM 自己已有“无新生产帧约 2 秒退出”的处理，但它不能证明网络黑洞、浏览器或路径异常时观众一定及时得到错误。[S08] `naturalWidth` 的定义是图像的固有宽度，不是帧时效指标。[W03]

### 今晚必须做到的下限

收到显式视频错误或来源切换时，撤销本控制端正在持有的手动输入；不能因恢复画面而恢复旧非零命令。保留旧画面时必须加明显遮罩与“画面失效/时效未确认”，而不是仍显示 LIVE。不要改用一个漂亮模拟场景填上真实画面的空缺。

若无法取得可信逐帧到达事件，标签应写“视频连接中/图像已载入，帧时效未核验”，且现场只能采用已放行的、操作者直接看得见机器的操作方式，不能批准仅依赖视频的盲操。现场观察并不替代 G01 或其他停车测试。

### 可实施的增强路径，不要误用 API

`<img>` 的 load/naturalWidth 不是可靠的每帧时钟，`requestVideoFrameCallback()` 适用于 `<video>`，不能直接加在 MJPEG `<img>` 上就称完成。静止场景也会产生有效新帧，像素差分不能充当心跳。[W03][W04]

可靠方案之一是在现有直连 CAM、合法 CORS 前提下，以有界的 multipart 接收器解码 JPEG：限制 boundary/header/frame/缓冲上限；只保留最新一帧；解码成功记录单调时间；切源递增 generation、abort 旧请求、忽略旧回调；恢复后要求重新按住，不续旧动作。精确限额根据真实帧大小测定，不抄猜测常量。

这需要浏览器、CORS、内存和 Safari 验证。今晚不能验证就降级，**不临时迁移 WebRTC、不新增代理服务器、不把视频转发压到主控控制任务**。仅增加一条 CAM“编码还在继续”的统计也不能证明浏览器收到新帧，两个指标应分开。

## 08｜C03–C06：控制台真实性与多端边界

### 急停确认必须看 robot 自己的年龄

V5 已复现 health-only 子块持续到达会使通用 stale=false，但旧 robot ESTOP 被继续称为设备新确认。当前 `stopStatus()` 调用仍使用通用 stale；本轮继承这条未关闭结论，不重复计入新测试数量。[S10][H01]

修复要保留本地 latch，同时以 lastRobotTs/连接状态/负年龄异常判定设备报告是否仍有效。UI 可以写“本地输入已锁，设备未确认”；任何 ACK/目标归零都不能直接升级成“车辆已物理静止”。

### 单路视频需要单一观看端

CAM `viewer.exchange(true)` 拒绝第二个流请求并返回 503。WS 支持多个 session 不等于视频支持多个 viewer。当前每个 WS 页面又默认打开 MJPEG，容易让电脑和手机互相抢流。[S08][S11]

明天用一台电脑控制并镜像投影同一画面，不要另开一张相同实时视频网页给大屏。第二终端默认仅遥测观察，只有显式操作才请求视频。识别出 busy 时说明“视频正在其他页面使用”，不要不停刷新占用 socket。浏览器 `<img>` 未给出 HTTP 状态时，不凭普通 error 擅称一定 busy；可提供可能原因和关闭其他观看端的操作。

### 切换来源、回放、隐藏与重连

打开本地视频、从真实视频切到模拟、进入回放、进入设置对话框或隐藏控制页面，都应先撤销当前手动输入。动作要由持有者或明确安全入口取消，不能让每个只读观察者因自己的视频坏了而反复发全局停止。后端租约仍独立存在，页面冻结时定时器未必继续运行。[W05]

当前视频选源回调只执行 `setSource`，没有将“视频会话变更”作为应用级事件交给控制器；应由协调层处理，而非把运动 Transport import 进视频模块。异步 load/error、旧重试 timer 必须绑定当前源代次，防止旧请求影响新源。[S07][S11]

### 模式不是自动许可

保留请求中、设备确认、拒绝和超时。只读状态不能用降低透明度一笔带过；给原因和合法接管方式。`send()` 成功仅表明浏览器成功排队，不代表 MCU 已执行。转动中、目标等待、前方阻挡、IMU 不可用、已取消分别显示，不统一写“就绪”。

## 09｜操作台的产品设计：像一件工具，而不是一张海报

Apple Home 的相机、配件与状态组织，以及 WWDC25 设计系统公开文字稿中的分组、层级与连续性，适合当软件参考。借鉴的是“重要内容可见、控制有稳定位置、状态不含糊”，不是把每一块都做成玻璃。[W01][W02]

### 建议的信息结构

第一层是设备/来源、控制角色和始终可达的急停；第二层是大而正确比例的实时视野、模式与按住式控制；第三层是手势结果、动作状态、健康与前方距离；最后才是版本、源龄、堆内存、原始日志等折叠诊断。

桌面沿用主画面 + 约 320–360 px 操作栏的工作台结构，摄像头按实际 4:3 内容 contain，不拉成宽屏；小屏顺序为视频 → 运动控制 → 健康，停止保持可触达。进入“观察/投影布局”可以减少诊断但不能隐藏急停、来源和权限。纯视频全屏会遮控制时，先停再进入，不为美观让停止按钮消失。

| 元素 | 具体要求 |
|---|---|
| 字体 | 系统字体栈；标题约 24–30 px、正文/控件 15–17 px、重要状态至少 13–14 px；投影另验 |
| 颜色 | 石墨底、实色内容面、一个蓝色主强调；红色专用于危险操作，警告另用文字 |
| 层级 | 同功能项分组，不把模式、状态、设置、回放挤在同一排 |
| 操作 | 运动控件按住生效、松开归零；停止一次触发；解除急停显式确认 |
| 目标 | 常用触控至少 44×44 CSS px，这是项目目标，不误称 WCAG AA 通用要求 |
| 动效 | 只用短反馈，不延迟停止；运行数字不触发布局跳动；不加舞台景深/背景粒子 |
| 数据 | 视频时效、识别时效、robot时效分别标记；缺值显示—，不填“正常” |
| 诊断 | 稳定入口、可复制版本和原因，错误持久显示而不是只闪 3 秒 toast |

**红色停止不应在刚收到确认后变灰得难以找到。** 可以改变文案为“本地锁定/设备上报急停”，但用户始终知道它在哪里。解除恢复与停止要明显分开。

本包的 `design/console-reference.html` 是可离线打开的样稿，带待连接、模拟操作、视频失效和回放状态。它没有网络代码，不是当前 `index.html` 已改好的截图，不得直接拿来控制设备。

## 11｜150 秒影片：补上移动、手势和操作台

V5 将运动融进了跟随，不足以清楚展示自由移动能力。本版建议 **150 秒，约 2 分 30 秒**：多出来的时间用于动作完整、反馈可读和操作台展示，而不是把现有镜头拖慢。时长是制作选择，不是必须超过短片才能高级。

| 时间 | 镜头与事件 | 主文案 |
|---|---|---|
| 00–07 | 白机身正面、OLED 微亮，稳定建立外形 | 认识这张脸。 |
| 07–20 | 顶盖/屏幕抬升、壳体让开、模块分区 | 小小机身，各有分工。 |
| 20–29 | 镜头、双超声端面特写与方向解释 | 看见位置，听见距离。 |
| 29–40 | 收拢，摄影机拉远到桌面和坐姿成人 | 刚刚好的小。 |
| 40–60 | 前进、后退、右移、左移、完整 360°，动作之间可辨 | **怎么转，都有范。** |
| 60–82 | 手势、识别标签、动作条件、转动/停止；LIKE 引到下一段 | 一个手势，心领神会。 |
| 82–98 | 新目标→朝向→跟随→丢失目标停止 | 跟得上，也停得住。 |
| 98–112 | 杯壁命中、回波、先停再受限绕行 | 先有判断，再向前。 |
| 112–130 | 真正可辨的手接触、采集、转 OLED、模拟结果、松手清空 | 轻轻一触，状态可见。 |
| 130–143 | 实际操作台样式，画面/目标/停止状态同屏 | **看得清，控得稳。** |
| 143–150 | 机身正面定格，舞台接回讲解者 | CareRover。现在，交给现场。 |

没有照片按钮、没有未经确认的自动开控制台，没有片尾自动运动。完整片用于较长答辩；短场次从同一分镜剪成 75–90 秒，保留运动、手势、控制台三个新增重点，不另造一套不同数据或模型。

配置在 `config/FILM_TIMELINE_V6.json`。它是制作脚本，不是成片文件；150 秒/30 fps 对应 4500 帧，索引 0–4499。

## 12｜“怎么转，都有范”：20 秒必须有真正的动作设计

建议机器人在同一张桌面的安全区域表演。开始保留一个小的“机头方向”视觉参照，不用旋转摄影机把左右含义搞乱。俯视或轻高位侧视能看出横移不改变朝向。

| 运动段局部时间 | 动作 | 关键视觉检查 |
|---|---|---|
| 0–4 秒 | 前进一小段 | 底盘平移方向与轮系一致 |
| 4–8 秒 | 后退到起点 | 不是突然 reset；自然减速与反向 |
| 8–11 秒 | 向右横移 | 机头朝向不变 |
| 11–14 秒 | 向左回位 | 身体不做无关旋转 |
| 14–19 秒 | 原地完整顺时针一圈 | 位置近似不变，角度连续累计 |
| 19–20 秒 | 停稳，OLED/文案轻反馈 | 给观众看懂“已经停住”的时间 |

位移数值是虚拟场景参数，不能当成设备速度或停止距离。本包示例使用 60 mm 的演示行程，不向机器人发送这些参数。

### 正交轮系不是四轮永远同转

生产 `omni_kinematics.h` 的归一化目标为 `[vx+wz, vy+wz, vy−wz, vx−wz]` 再统一限幅。前后移动主要由纵向轮对主动驱动，横向轮对依靠被动滚子允许位移；横移相反。展示必须按实例轮轴符号映射，不照搬麦克纳姆或 X-drive。[S12]

360° 动画使用连续角度或积分行程。0° 和 360° 的四元数端点相同，直接最短路径 slerp 可能看起来根本没转。测试中应检查中间 180°、终点 360°和机器人位置，而不只比较首末姿态。

手势真实旋转还有 IMU、12 秒动作截止和物理惯性约束；片中的五秒一圈是虚拟编排，不能直接要求今晚实车按同速度动作。现场转动幅度与速度只使用已测、可停止的范围。

## 13｜手势与 OLED：让人、判断和动作真的关联

影片里同一个人可以先举 TWO（或 THREE），画面显示识别标签，随后机器人按当前动作映射回应，最后 DISLIKE 停止。LIKE 在后段衔接人脸跟随。不要塞进五种近乎相同的完整旋转，让观众只记得“转了好久”。

动作前保留一点确认停顿、显示框与简洁状态；转动开始后不把检测框的出现当成唯一执行凭据。模拟 OLED 可显示 `G:TWO`、`G:LIKE` 等标签，具体字体和真实屏幕布局由现有 OLED 能力核对。[S06]

### 人和手要符合图像中的实际比例

成人在桌边，手伸到低位摄像头能看到的位置；不是一个小人站在桌子上。影片应检验手在虚拟 320×240 图像内是否足够大，尤其动作框高度门槛接近画面一半。镜头/手/脸的空间关系要先做分镜验证，而不是把软件门槛删掉适配远处的小手。

### 健康镜头保留同一事件

手腕、掌部、指腹可辨；接触面用健康模块锚点定位。接近、采集、结果、松手独立阶段。虚拟 `healthDemoState` 决定同一组 72 BPM / 98% SpO₂ 的示例结果；转到 OLED 不重新随机数字。持续标注“模拟读数，采集过程已压缩，非医疗用途”，真实网页只从有效设备数据取值。

光效只解释接触附近的红光/红外采集，不表现成隔空激光测健康。摄像头可有科技感角标或薄视域，但不是物理激光发射器。杯子场景展示前方测距与受限路径，不暗示侧后方感知、全向避障或防跌落。

## 14｜一个导演，多种入口，探索不破坏剧情

保留 V5 的统一 `evaluate(t, viewport, quality)` 设计：相机、部件、人、手、杯子、机器人、OLED、字幕由同一可查询时刻产生。Scroll 映射位置，Deck 按章播放到 hold，Film 固定步长采样。视频播放时以媒体时间为主，不再与另一个 rAF 累加时钟竞争。

进入自由探索暂停影片/声音并保存语义时间；退出回到原位置且保持暂停，让讲解者主动继续。默认完整、细鼠标停留后展开、选中锁定、关闭说明回总览、主动收拢；触屏按钮展开，双指缩放，退出稳定可触达。

三套布局继续独立：StoryOpen、InspectExploded、PartFocus。外壳、主板外框、主板、支架、电源与传感器组各有清楚的空间槽位。扩大位移要结合路径和相机安全区，不只是乘一个系数。360° 任意角度都没有二维遮挡不现实；要求三维无非设计穿透、默认总览可读、选中后重点无遮挡。

### 影片产出

首选高质量离线人物/手部镜头 + 轻量实时探索的混合方案。输出 1920×1080、30fps、H.264/yuv420p、SDR MP4；有配乐和无配乐至少一种符合现场方案，字幕与关键文本离线可用。长片渲染要先做 8–12 秒试片测资源和时间，不在最后凌晨才首次导出。

网页可以播放同一 MP4，Deck/Scroll 保持可控。导出使用确定时间采样和完整 DOM 合成，不依靠模拟慢滚屏录制。QA 操作录像与发布影片分开命名，不能把 `story-tour.webm` 重命名当新发布片。

## 15｜今晚：烧录不是最后一键，而是一次有退出条件的发布

今晚的顺序是：**软件候选固定 → 真实设备识别 → 备份 → 正确设备构建 → 受控烧录 → 分层验收 → 冻结**。组员电脑上未推送改动先保存并比较，不能强制 reset 覆盖。[S13]

### 构建与版本

核对实际两块板、串口、Flash/PSRAM、FQBN、电源、轮位、IMU +X、传感器和标定存储。不要假定历史 COM3/COM6，不填猜测 GPIO、距离阈值或 NVS verified 值。私有 Wi-Fi/board/front 配置不提交仓库，已经泄露的旧口令需要现场轮换并同步两板。

现有资料中的包是 compile_only，不能只改 verification 字段就烧录。使用项目已验证工具流程和实际 local profile；保留完整 Flash/NVS 备份、读取校验与成套回退。不要为网站样式执行整片擦除，不删除 NVS。[S13]

**控制台 JS 变了就要重建 FFat。** `presentation/`、人物资产和影片不放进 ESP32 FFat。CAM 没改源码不代表其现场固件版本可以不检查；若只是主控 Web 更新，避免无必要地同时重刷所有部件，减少引入变量。

### 分层放行

| 层 | 做什么 | 不能偷换的证据 |
|---|---|---|
| observe / 动力隔离 | 摄像头、UART、OLED、IMU、健康、网页来源 | 传感器有数不等于动力安全 |
| 架空、现场可断动力 | 每轮极性、中位、所有输入释放、断 WS、手势普通停止 | target=0、PWM回中位、轮停分别记录 |
| 受控低速 | 前后左右、转向、目标丢失/恢复、已验证前方保护 | 场地/速度/供电/版本一致；不以60%归一化猜真实速度 |
| 故障与长时 | 既定失效用例、G01、无线无USB十分钟、冷启动 | 一个路径失败就撤下对应动作，不平均成总体通过 |

G01 未通过时，明天采用 observe + 影片/明确回放，不做该未放行固件的现场动力动作。旁边站一个人并不能让未证明的独立撤销机制变成已通过。

## 16｜今晚必测的停止与反馈矩阵

所有实物故障测试在动力可隔离、底盘受控的条件下由现场人员执行；不在桌边或人脚边拔线试错。下表是待执行门，不是本报告已完成的结果。

| 用例 | 输入/扰动 | 期望 |
|---|---|---|
| 手动 deadman | 停发 cmd_vel，ping 继续 | 有限期限后零目标；不续旧速度 |
| 断控制通道 | WS断、AP还连 | owner动作停止并释放；重连不继承输入 |
| 键盘/触摸 | 松键、指针取消、失焦、锁屏 | 撤销所有相关分量，重新按下才恢复 |
| 视频独立失效 | 视频无新帧，WS与识别元数据继续 | 不显示假LIVE；视频操作策略正确，不能盲操 |
| 源切换 | 手动按住时切本地/模拟/回放 | 原输入撤销；新源不自动发动作 |
| 人物失效 | 显式未找到 vs P消息全静默 | 都撤销无依据输出；等待与退出符合期限 |
| 手势交接 | 手动→待机→手势、所有者/观察者组合 | 合法路径能接受、非法路径拒绝且解释，不出现隐藏夺权 |
| 动作取消 | 转动中普通停止，继续输入新IMU | 不复活旧旋转；超时不依赖下一个回调 |
| IMU 故障 | 无效/拒绝/倾倒后丢样本 | 不把未知当恢复，不自动恢复旧动作 |
| 超声失效 | 已配置保护下断输入/各绕行阶段取消 | 撤销动作；未配置则明确未启用 |
| G01 | 受控暂停安全任务/等价故障 | 由独立机制实际撤销PWM及运动，测量证明 |
| 视频独占 | 第二浏览端打开视频 | 有可解释限制；主操控不被误认为全系统断线 |

每个核心停止场景建议先重复若干次，任何无法解释的非零残留都阻断对应动作。记录 event→target→PWM→实体停止的时间，而不是只录网页数字。今晚来不及完成所有功能验证，优先缩减明天动作清单，不放宽条件。

## 17｜明天的答辩流程：先吸引，再解释，最后证明

建议主流程约 **8 分钟**，如有正式限时，以老师要求为准。操作者与讲解者尽量分工，另一个组员负责场地/动力停止；影片播放时保持机器人停止，避免镜头中的模拟动作同时被真人手势误触发到机器。

| 舞台时间 | 行为 | 讲解和检查 |
|---|---|---|
| 0:00–0:15 | 一句话介绍问题与项目 | “我们做了一台桌面移动原型，把视觉、手势、测距和接触式测量连成一个系统。” |
| 0:15–2:45 | 播放150秒影片 | 不手动滚屏；末帧停住，不自动连接设备 |
| 2:45–4:00 | 自由探索解释三组结构 | 整体→开壳→视觉/主控/轮系；只讲因果，不点遍十五个部件 |
| 4:00–4:30 | 进入操作台，说明来源和权限 | 让观众看到真实画面、robot状态、控制目标；确认动力演示已放行 |
| 4:30–5:30 | 手动前后/横移与一次停止 | 操作者现场直视机器人；松手停是演示内容，不只让车跑 |
| 5:30–6:30 | 手势识别或已验收的一个自主动作 | 控制权必须预先排练；未放行就只看识别/OLED，说明条件 |
| 6:30–7:30 | 健康/OLED或故障边界说明 | 真实采集可能较慢，先显示采集中；不为赶时间假填结果 |
| 7:30–8:00 | 结束，回待机并撤销授权 | 总结已实现与边界，准备提问；不保留待执行动作 |

健康测量可在讲解中提前开始（机器静止、操作者准备好），但不能让无关手势意外启动动作。项目现场应先确认手势引擎的准入状态，必要时使用已经验证的只读/observe展示路径。

### 五分钟紧凑版

开场10秒 + 同内容剪辑的75–90秒影片 + 结构50秒 + 操作台30秒 + 已放行实际动作60秒 + 结果与边界40秒。没有额外时间就删重复的第二次旋转，不删来源说明、停止验证或结束归零。

### 故障时怎样不失控也不尴尬

画面异常或动作不符，操作者先停并确认实体；讲解者说明“当前演示切换到已标注的记录/结构讲解”，不遮掩失效。不现场搜索串口、不强行多次点模式、不临时刷固件。影片/结构页仍可离线使用；没有实物通过证据就不把录像改称实时。

## 19｜最终验收：不是只要漂亮，也不是只要测试绿

### 媒体与网站

### 操作台

至少检查待连接、连接中、只读、手动、跟随等待、手势仅识别、动作执行、视频坏而WS好、WS坏而旧画面还在、局部遥测、急停本地锁/设备报告、健康采集中/保持/无信号、回放以及返回实时。没有真正设备确认不能显示“已停止”或“已执行”。

### 实体

G01、当前配置/标定、主要停止路径、选定动作与无USB长时记录是独立条件。不得仅用UI sample或影片给实体签字。最终状态表模板 `config/RELEASE_ACCEPTANCE_TEMPLATE.json` 默认全是待执行，不自动把旧CI通过抄入新包。

**现实的“不能出错”不是承诺没有任何故障，而是：已知风险先排除；不确定状态能辨认；错误不继续授权动作；现场有可验证的停止与降级路线。** 这比堆更多未排练动作更可靠，也更能体现工程完成度。
