# CareRover｜实物外观与深色产品叙事制作规范

**第四版 · 2026-09-18 · 面向下一轮 Codex Goal**

**结论：现有 CAD、两张不同视角的实物照片和九类器件资料，已足够启动可信的外观制作。整车扫描不是前置条件。** 本轮不再要求先补齐全套六面照，也不要求推倒模型或重写控制台。先完成一段真正可看的“完整正面 → 开壳 → 摄像头近景”，再延展其余故事。

本文件将“像我们的机器人”“有产品级视觉表达”“能在答辩中可靠播放”转成可执行的资产、镜头、代码与验收契约。它不是已经完成的写实 GLB、网站或实体测试证明。

基线：`NeedleAss/spider-webite-dev`，`codex/final-polish`，PR #1。此次复核 PR head 仍为 `72ee475bd76b7a46f2c3bd6477dcd2f45b76ac69`。第 3 版安全审查继续有效；本版追加实物资料与制作规格，不把旧测试重新算成本轮通过。[R1]

交付包附有 11 张裁剪参考图、器件/材质/线束/分镜 JSON、第四舵机原始安装矩阵、深色设计变量及 14 项通过的纯函数示例测试。**实际可确认的物件、拟完成的装配、说明性动画，三者分别记录。**

## 01｜新照片改变了什么

![当前实物正面参考](references/robot-front.jpg)

*F01：用户当前未完成组装的实物。显示屏位于顶盖；正面两个圆孔用于超声通道，下方小方孔用于镜头。不是最终装配或性能验收照片。*

### 可以直接固定的事实

机身主体是白色打印外壳；顶部是黑色窗口、蓝色单色发光的 OLED。两个圆孔和下方镜头孔共同形成正面特征。用户明确说明电源位于底部，IMU 与手指接触的健康模块分置侧面，内部主要通过柔性线束连接。用户明确给出四轮、四个 MG90S 360° 舵机。[F01、F02、U1]

因此：上一版收集单中仍保留的“屏幕是否在侧面”“到底三个还是四个舵机”，不再是库存层面的开放问题。OLED 固定在顶盖；目标装配按四个舵机设计。但第四个舵机实际安装到位、最终线束走向和超声端面深度，仍不是这两张照片已经证明的事实。

### 照片不应被过度解读

正面两个圆孔尚未呈现完成安装后的两个齐平金属端面；不能把孔洞误当作另一种传感器外观。抬起的盖板、松开的壳体和桌面线缆反映组装过程，不应无说明地变成成品永久造型。第二张内部照被重复发送，只有一个视角，不是三组扫描资料。

外壳的精确宽高、镜头凹入量、全部引脚连接和电池节数，不能从手掌比例或透视照片补成测量值。背景卡片及无关个人信息不进入公开网站；本包参考裁剪排除了内部照右上方卡片。

## 02｜已经具备的资产，与必须保留的依据

### 本轮实际做了什么

重新使用第 3 版已核验的导出脚本读取原始压缩包，仍得到 15 类保存显示网格、20 个可见实例、701,560 字节 GLB。SHA-256 为 `2310e2bd46a6940497349d1acf00ef70bd8279881a637424b2764c136229d61b`，与先前候选一致。原装配含 21 个引用，其中第四个舵机为隐藏，不是没有建模。[E1]

本轮提取了该隐藏舵机 reference 7 的原安装矩阵，见 `config/hidden-servo-restoration.json`。目标装配可在衍生模型中恢复这一实例，再与实际安装核对；不要用镜像复制猜位置，不要修改原装配的历史证据。

这是保存网格/矩阵复核，不是原生 SolidWorks 配合、当前配置或制造精度验收。没有重新生成 B-rep，也没有产生新的全写实模型。

### 信息优先级

有确定的最终实物测量与安装记录时，优先采用；其次是用户照片和明确修正；CAD 提供已有安装基准与相对位置；精确同型号资料补充部件外形；只有最后才使用有标注的美术近似。任何冲突先记录，不能把“有 CAD”理解成“每个长块都是真实零件”。

| 资料 | 当前能解决什么 | 不能替代什么 |
|---|---|---|
| 原始 CAD | 层级、位置、结构关系、已保存实例变换 | 成品表面、线束、最终可见性 |
| 实物照片 | 顶部 OLED、白壳、正面孔、实际配线形态 | 精确尺寸、遮挡内部、完整电气连接 |
| 用户器件清单 | 9 类器材、4 轮、4 舵机、预期型号 | 商家具体 PCB 版号、参数标定 |
| 商家截图 | 轮型、外壳、排针、丝印与材料类别 | 实测、公版通用外形、公共贴图使用许可 |
| 官方器件资料 | 核心芯片功能及对应产品的标称规格 | 第三方载板外形、实物装配和性能 |

## 04｜型号研究：找到参考，不等于确认同款

### 可使用的官方依据

乐鑫 ESP32-S3 官方资料说明处理器最高 240 MHz。用户开发板商品图里的“550M 主频”不能进入项目说明。N16R8 是所购板的标识依据，不能据此推定任一 N16R8 开发板外形和接口都相同。[W1]

TowerPro 的 MG90S 页面给出该产品族 22.8×12.2×28.5 mm 等尺寸，可作为轮廓检查参考；它不是用户所购 360° 变体的安装与控制标定。用户“360° ×4”的声明优先用于本项目动作类型，不从商家混合了 180/360° 的缩略图倒推电气参数。[W2]

Analog Devices 的 MAX30102 资料确认其集成 LED、光电检测等部件；红光与红外解释可以使用。但芯片尺寸不等于白色载板尺寸，芯片功能也不等于你们整机已达到医疗测量精度。[W3]

### 本轮未确认的精确商品资料

没有找到足以独立证明“鹿小班这块 PCB 版号”“该黑色摄像头载板的传感器型号”“18650 电源模块内部拓扑”“24158 的制造商原始尺寸图”完全匹配本机的官方资料。因此，不从相似网上图片填补电路或机械事实。现有用户截图反而是更贴近本机的外观参考。

HC-SR04 商品页混有电压/版本选项；OLED 也有针脚排列和 PCB 版本差异。应按本机对应图建外观，不从一个模糊搜索结果继承供电或引脚结论。这个区别不阻止视觉制作，只限制未经证实的参数宣称。

网上图片可以辅助比对。未获许可的商家图片作为私有建模参考，不直接裁成公开网站贴图，不去水印冒充自有素材。公开渲染优先使用自行制作的几何、丝印与自有照片。

## 05｜写实路线：保留 CAD，替换外观，不重做整机

建议资产树采用三层：**安装与结构基准 → 实物外观 → 展示动画**。第一层回答放在哪里，第二层回答长什么样，第三层只改变讲解姿态。替换 PCB/轮组细节时，不把 CAD 安装位也一起重置。

每个可交互实例保留 partId 和 instanceId；外观可以拆成多个网格，但它们归属于同一实例。新的 wheelAppearance 不应使四轮缩成一个类型节点；恢复第四舵机也必须保留独立身份。

### 外观替换以基准点对齐，不以包围盒硬拉伸

轮子使用轴心、轮平面和接地半径；舵机使用输出轴、安装耳、底面；相机使用镜头中心和光轴；超声使用端面中心及法向；板件使用安装孔、接口和板面。缺少尺寸时先保留 CAD 基准，外观标为近似，不将任意下载模型拉伸到整个代理块包围盒。

本轮保存网格的 wheel 局部范围约 23.3×23.254×18.4 mm，而商家标称是轮径 24 mm、胎宽 15 mm。两者不自动冲突：包围盒可能包括联轴器，且不能把三轴范围当作轮径、轮宽、安装深度。更不应因此按比例缩放整个机器人。[E1]

### 先做轮廓，再做表面

优先轮子滚子/联轴器、相机镜筒、超声端面、PCB大件、OLED玻璃与接头。丝印、小电阻和焊点可通过贴图/法线补充；不必给每个小器件都建独立高面数网格。上壳保留白色打印质感，不改成照片里不存在的铝合金或陶瓷。

交付目标是“有依据的实物外观重建”。没有完成尺寸测量与扫描校验时，不称毫米级扫描复刻，也不称数字孪生实时镜像。

## 06｜线束：把假长块改成真实连接，而不是另一种装饰

![内部线束与顶盖背面参考](references/robot-open.jpg)

*F02：彩色柔性导线、顶盖 OLED 背板、内部板件和支架。部分端点被遮挡；该图不构成完整接线图。*

### 先正确删除代理

用户已经确认主板下两条长矩形只是杜邦线占位。可在衍生网格中分离并替换；原始 CAD 保留。不能用“低于主板的全部顶点”“最长两个连通块”等规则盲删，尤其保存网格有重复顶点和合并的零件几何。先给代理区域做可见标记，经人工核对后删除，前后截图留档。

### 用少量有意义的线束组组织视觉

按顶盖屏幕、摄像头、前方测距、侧面 IMU、侧面健康、电源与四个执行器分组。保留照片能确认的颜色与大致路径；整理展示不等于伪造端点。被线遮住的插针先写 endpoint=null 或仅表示“模块间关联”，不要依据红黄蓝颜色猜 GPIO。

建议低模曲线管线配合黑色杜邦接头。管径、长度属于待确认物理尺寸；没有数据时可以用明确标记的视觉近似。曲线进入接头时方向应连续，不能悬空、穿板或穿过螺丝。

### 拆解线束的三种可接受处理

优先使用有限拆解幅度，让线束在原长度内改变弯曲。需要更大爆炸图时，可明确表现“连接示意已简化”，淡出非重点线或展示接头拔开后的两端。任何情况下都不把导线无限拉长。

生产实现可使用少量控制点和弧长约束，不需要临交付引入软体物理。对每根可见线检查端点距离不超过设定长度；大镜头只显重点线束，不能让全部彩色线盖住主板。`CABLE_CONTRACT.json` 明确记录未知端点，不能作为电气接线依据。

## 07｜材质与灯光：深背景，白机身，少量蓝色

采用深石墨背景和真实白色机身。单一冷蓝/青蓝强调色来自实际 OLED。**精简的是界面颜色，不是把实物 PCB、标签和导线全部染成同一种蓝色。** 外观保留蓝板、黑板、银色金属和少量彩色线束，才有真实感。

| 材料 | 建议起始 metalness | 建议起始 roughness | 最重要的可见特征 |
|---|---:|---:|---|
| 白色打印塑料 | 0 | 0.60–0.78 | 柔和边缘、轻微层纹，不能像镜面瓷器 |
| 黑色橡胶滚子 | 0 | 0.65–0.85 | 滚子分界、柔和高光，不是一团纯黑 |
| 深色舵机壳 | 0 | 0.30–0.50 | 安装耳、接缝、轴和标签；半透明仅近景高档 |
| PCB 阻焊 | 0 | 0.40–0.60 | 大色块与丝印，金属焊盘独立处理 |
| 换能器/螺丝金属 | 1 | 0.22–0.40 | 银色端面、细网纹、控制高光不过曝 |
| 镜头/屏幕窗 | 0 | 0.06–0.22 | 深色玻璃反射和透镜层次，不能整块发光 |

这些数值是美术初值，不是实物材料测量。物理材质使用 metallic-roughness 工作流，颜色贴图与非颜色数据需使用对应色彩空间；环境反射对于金属和玻璃可读性很重要。[W4]

主光用柔和的大面积效果塑造白壳；弱补光保住内部黑件；窄轮廓光将轮子与背景分开；地面只保留接触阴影和克制反射。没有环境细节时，镜头不会因把 roughness 降低就自动变真实。不要用强 bloom 掩盖建模，不能让白壳过曝到孔位消失。

图像白平衡可作为视觉参考，但照片中的木桌暖光不等于外壳本身是黄色。单独保留未经调色的参考图，衍生宣传图的打光不回写到几何事实。

## 08｜传感器方向：建立永远正确的安装坐标

本资产仍是 CAD 世界 up=+Y，正面=−X；camera 与 ultrasonic 局部 +Z 经各自保存矩阵变成世界 −X。原展示的 world +Z 线条不能继续使用。本轮重新导出确认了这一方向。[E1]

建立节点：实例安装变换 → 器件外观 → 传感器锚点 → 说明效果。镜头锚点在光学中心附近；超声锚点在换能器端面；不在整个部件包围盒中心。继承父级姿态后，整车转动和零件拆解都不能改变相对光轴/声轴。[W5]

`SENSOR_ANCHORS_V3_REFERENCE.json` 只是绑定旧 GLB 哈希的几何候选，不能直接当成精细外观的永久坐标。加入更真实的镜头/换能器后重新检查锚点位置，保持前方定义不变。真实 FOV、波束角、TX/RX 未确认时，保留“视域/回波示意”，不写角度或收发身份。

### 单位和相机必须分清

CAD与GLB局部单位是米；旧展示根节点放大1000。可暂时在适配层保留该比例，但新传感器子节点仍用米，不能塞入旧世界毫米数值。Three.js 摄影机看向局部 −Z，不等于自定义说明效果的 +Z。不能为了修网页视觉去改 IMU 轴或机器人指令轴。

首页摄影机放在传感器正前方侧，建议近正面偏航约 10°–20°、略高约 10°–18°作为美术起点，同时看清顶盖 OLED。该角度不是固定硬编码结论，应随纵横比构图；首屏、重置、收拢终点和静态海报使用同一已验收镜头。

验收时用端面法向检查：光轴/声轴朝外，效果从对应端面起；相机旋转、爆炸姿态、窗口变化后仍成立。除了数值方向，还要以用户实物正面照核对，避免数值自洽但安装理解错误。

## 09｜苹果式表达：借鉴产品叙事，不复制素材

本轮再次查看 Apple 的 iPhone Air 与 MacBook Pro 官方产品页，参考它们如何在整机、内部细节、相机/性能与使用场景之间切换内容重点。不将这种观察包装为已逆向验证苹果每个动画的实现，也不假定所有片段都是实时3D。[W6、W7]

CareRover 的视觉主张是：**深色留白，真实白色机器人，一次只讲清一个动作。** 首屏不是仪表盘，也不是十五块小卡片。技术细节进入当前部件的短说明或最后的探索目录。

| 章节标题/正文 | 标题约 32–60 px；正文 16–20 px，行高约 1.6；关键标签至少 12–13 px |
| 比例 | 首屏机器人约占可用高度 55%–68%；文字不压住“脸”；微距镜头独立放大 |
| 布局 | 12 栏思路，正文约占 4 栏、物体约占 8 栏；手机改上下结构，不强挤左右栏 |
| 色彩纪律 | 每章最多一个 UI 强调色；红色主要留给真实错误/停止解释 |

在本包六组纯色文字/背景组合中，最低对比度约 8.04:1；这只是 token 配对计算，不代表整站已通过无障碍验收。W3C 对普通文本的基本门槛是 4.5:1，大文本为 3:1；实际应检查字幕叠到模型和光效时的背景。[E3、W8]

高对比不等于薄字体也可读。投影时保留字重、减少半透明小字；不要通过把文字缩成 9 px 制造“精致”。控件与文案在中英文切换后不挤压停止或章节导航。

## 10｜七章故事：结构、功能、运动与实物闭环

| 章 | 屏幕上发生什么 | 文案方向 | 不应出现 |
|---|---|---|---|
| 1 认识 | 深色背景中完整正面，顶盖屏幕微亮，稳定停留 | 先认识，这张脸。 | 开场自动旋转到背面、鼠标一碰全炸开 |
| 2 打开 | 顶盖与屏幕先抬升，壳体后分开；板件层级有秩序 | 打开之后，各有分工。 | 十五件随机散开；线无限伸长 |
| 3 看见 | 镜头近景，目标进入同向视域，框与图像一致，车作简短回应 | 看见位置，作出回应。 | 身份识别、激光发射、目标在镜头背后仍被框住 |
| 4 测距 | 双端面近景，波到障碍再返回，显示前方距离判断 | 先看清前方，再向前。 | 垂直发波、侧后方未知却宣称安全 |
| 5 行动 | 整车重新合拢，在简洁地面前进、横移与原地转向 | 不转身，也能横移。 | 漂浮、车向前轮向后、四轮永远同向 |
| 6 关怀 | 侧面手指接触区域，简短光学解释，再切顶部 OLED | 轻轻一触，状态可见。 | 非接触测血氧、假健康正常值、全彩 OLED |
| 7 回到整机 | 精确收拢与首页相同镜头，转到用户实物记录 | 从一张设计，到一台实物。 | 未完成照片被说成已验收成品 |

每章通常一条短主标题、一段不超过约60个汉字的主要解释；更深的内容置于“了解细节”。这是建议排版限制，不应通过删掉关键真实性说明凑字数。完整分镜在 `STORYBOARD.json`。

主控并不需要再增加一整屏密集仪表。可在“看见/测距→行动”的过渡中用一条简短信息路径解释裁决：观测有效才形成输出；失效时撤销。这样把安全设计讲清楚，又不打断视觉节奏。

## 11｜让动画有情节，而不是一直循环

### 摄像头：目标与机器人发生关系

建议一段约 6–8 秒的自包含场景：目标轮廓进入前方 → 图像平面上产生人脸框 → 目标偏左，机器人先朝向它 → 再形成前后跟随示意 → 目标退出，机器人停住。位置与动作顺序应与当前“先转向再平移”的演示配置一致，不把卡通角色的移动当成实际识别日志。

使用简洁的人物轮廓、轮廓手势或团队自有短视频。不要用陌生人的人像暗示已获取许可或已识别身份。屏幕结果标注“原理演示/模拟轨迹”，用户进入真机控制台时再切换数据标签。

### 超声：一束波解释一次判断

波前从模块正面发出，在同轴障碍位置接触，随后回到模块。视觉上可将不可见声波染成强调色，但这是说明性可视化。没有确定TX/RX时用模块级发出/返回，避免精确指定错误端面。

可插入一段整车遇到单个障碍、停止、按既有受限流程向右绕行的镜头；右侧与出口是预先给定空旷场景，不演成机器人感知了全部方向。实物未通过绕行验收时，标签写“受限场景原理动画”，不写“实测自动避障”。

### 轮组：整车动作与轮子不能互相矛盾

现有 `omni_kinematics.h` 明确采用两组正交主动轮对，而不是 X-drive。归一化混控按 FL/FR/RL/RR 为 `[vx+wz, vy+wz, vy−wz, vx−wz]`，再统一限幅。前进时纵向对主动，另一对靠被动滚子允许位移；横移相反；不能把四个主轮始终同向转动。[R2]

展示用混控示例已附并测试；它不提供真实角速度。制作时给每个实例标定轴心和正转方向，用几何行程/半径或一致的演示比例驱动角度；实体舵机的电气反向参数不能直接当网页轴向。没有被动滚子动画的余量时，避免极近距离暴露明显滑行。

### 多机与户外镜头：可以编排，但不能扩大能力宣称

可选做 2–3 个同模型的独立轨迹镜头，作为产品视觉编排。用户提出这类动画是允许的展示方向，但它不是多机协作、编队控制或避碰的实物证据。默认优先完成单机；末两天不因此新增机器人协议或群控系统。

户外/生活场景优先团队自有短素材或明确的场景合成；不要让一段漂亮画面暗示已经具备户外导航、防水或复杂路面能力。场景只是让功能易懂，不能替代工程边界。

## 12｜交互与运行时：滚动叙事、自由探索分离

默认 Story：鼠标滚轮、触控板、触屏和键盘驱动原生页面滚动。一个 sticky 场景呈现当前章节，DOM 文本保留可选择、可访问与静态阅读能力。滚动不同时被 OrbitControls 用来缩放。

Inspect：明确点击“自由探索”后才启用旋转/缩放与部件拾取；退出返回原章节。没有选择时，悬停最多轻微强调，不再自动完全拆开。章节目录/上一章/下一章要有普通按钮或链接，不能只靠手势。

### 一个进度对应一个确定姿态

滚动位置得到 progress，再由不可变 rest TRS 与关键帧计算最终 TRS、摄影机、材质、文案和效果。向上滚、快速跳章、刷新到中间都应得到相同画面；不在当前位置上重复累加offset，不让多个 tween 同时争抢同一相机。

剧情有两个时钟：章节姿态跟随滚动；部件内部短动画可按当前章的独立演示时钟播放。后者离开章节即暂停/复位，循环只在已允许播放时进行，并提供暂停。禁止把全局 Date.now() 当唯一叙事时间，导致每次进入看到不同的半截镜头。

移动端 Story 与静态 fallback 允许 pan-y。进入 Inspect 才在明确的交互区域暂时接管手势；从画布中心向上划也必须能翻页。减少动态效果时提供静态关键帧，不把整篇内容隐藏在无法播放的动画里。

页面可见时才渲染；静止时按需重绘；同一 WebGL renderer 复用所有章节。模型载入失败保留正确正面海报、文字和目录；WebGL 恢复时回到原章节，而不是强制回首页。

## 13｜代码边界与文件级实施建议

保留原控制台、固件安全边界、+X IMU安装、原阈值和NVS校准。本轮新增的舞台光、镜头与模拟人物不进入运动控制链路。独立 `presentation/` 继续不连接 WebSocket、不引入控制 Transport、不进入主控FFat。[R1、R3]

| 建议文件 | 单一职责 |
|---|---|
| `presentation/story/timeline.js` | 章节进度、镜头与部件姿态关键帧 |
| `presentation/scene/asset-adapter.js` | 原CAD/衍生外观映射、单位、partId/instanceId与安装基准 |
| `presentation/scene/sensor-anchors.js` | 镜头/超声端面锚点与法向；不读取固件传感值 |
| `presentation/scene/cables.js` | 有端点证据的曲线线束与大拆解淡出策略 |
| `presentation/effects/vision.js`、`sonar.js` | 当前章节的原理动画与单独局部时钟 |
| `presentation/scene/motion-demo.js` | 按现有轮系的演示轨迹，不发命令 |
| `presentation/ui/story-controls.js` | 原生滚动、Inspect、键盘、减少动态效果及恢复 |
| `presentation/assets/appearance/` | 衍生模型/贴图/海报及来源清单 |

不要为了文件数而机械拆分，现有入口保留初始化和销毁即可。层级变化后不能继续假定 model.children 每个都是一个零件；遍历时以命名节点/元数据识别交互实例。效果必须绑定选中的 instanceId，而不是总取同类的第一个网格。

选择时非重点件降亮度即可；不必把全部零件设为半透明。真正被淡出的结构不能继续抢射线点击。按 pointerId 区分单击、拖动、多指取消；非交互图片/文本不能阻止页面滚动。

代码已知收尾另行小提交：急停本地锁、发送/确认状态分别显示；回放文案优先于实时stale；PPG区分采样时间与接收时间。第3版问题仍按原验收关闭，不把它们与美术重写混成不可回退的大提交。

## 14｜三种渲染方式如何分工

**主方案：CAD基础上的实时3D，负责可逆结构展示与部件交互；少量预渲染片段负责高质量情境；真实照片负责最后对照。** 不把任意照片当作可以从全部角度观看的3D资产。

实时3D先覆盖整机、开壳、相机/超声近景。若金属网面、玻璃或多线束近景仍不够好，用自制高质量预渲染视频或有限帧序列补充，不要求所有镜头硬塞进同一GPU实时效果。离线交付时同时保存海报，媒体未解码就显示海报，不留黑屏。

帧序列会占用存储和解码内存，视频seek也不一定帧精确；本轮不承诺任一方案天然比实时更轻。首先在目标Mac和手机测冷启动、滚动与内存，再选择必要片段；不要全片4K序列预加载。

### 建议的工程预算，不是硬性行业标准

首屏先交付轻海报，核心整机与贴图优先争取约 3–6 MB，近景细节分章懒加载；需要超出时记录原因和测量结果。桌面可先争取200k以内可见三角形、手机120k以内；draw calls尽量低于100；关键交互手机30 FPS作为起步目标。不能因为GLB压缩小就忽略贴图在GPU中的解码占用。

每次只运行一个章节效果，默认不全局bloom/实时景深。接触阴影和环境光先解决体积，再评估更多后处理。保留当前本地Three.js版本，首次不引入必须联网的字体、解码器或素材CDN。

## 15｜扫描是否还值得做

**不用等明天扫描，当前制作即可开始。** 最缺的是同款器件外观和若干安装细节，不是整车位置关系。你已经有CAD装配，扫描不是唯一补足方式。

Apple Object Capture 官方建议对象具有足够纹理，透明、少纹理和强反光区域容易缺细节。白壳、玻璃、金属网面与细线的组合并不适合期待一次整车扫描自动解决全部问题。[W9]

扫描作为可选参考时，先保持同一静止装配和光照，用连贯且有重叠的多角度照片；不要一半照片盖着壳、一半开着壳混成一次重建。被盖住的内部不能靠扫描看到；也不会自动生成可独立拆解的PCB、螺丝和真实电气连接。

本轮只在最终近景缺乏某个独特部件形态时，才考虑补拍或单独扫描该部件。若明天顺手能拍，只需最终装好后的正面照、一个能看清接口/型号的近照或一句安装深度确认；不是再次要求全套摄影任务。没有补充资料的区域先保持有标注的简化，不阻塞第一段展示。

## 16｜最短可交付路径与验收门槛

### 先交一条完整、可看的短流程

第一阶段完成：传感器正面整机、顶部OLED、正确轮组轮廓、开壳顺序、相机近景与同向检测情节。把这一段在1366×768和390×844录下来，先验收正反滚动、图文比例和真实感。没有这段就不要继续堆七个空章节。

第二阶段补超声、线束、轮组动作和健康/屏幕镜头。第三阶段做资源降级、同角度实物收尾、两次冷启动离线彩排。多机/户外只在单机通过后加，绝不挤掉失效停车和现场联调时间。

| 验收维度 | 必须达到 |
|---|---|
| 事实 | 顶盖OLED、前双圆孔/小镜头孔、白壳、4轮4舵机、真实PCB风格；未确认处有记录 |
| 外观 | 轮子不是圆柱；镜筒/超声端面可读；假杜邦线块已正确替换；无明显穿模 |
| 坐标 | 合拢/拆解/近景/整车转向下，效果都从端面沿模块前方出发 |
| 故事 | 不用拖动也能看见被讲解的部件；每章有起点、动作和结果；回滚不漂移 |
| 运动 | 轮系与既有正交混控一致；壳体/舵机壳不跟轮子一起转；无悬浮/反向滑行 |
| 手机 | 画布中心能纵向滚动；Inspect可退出；横屏/200%缩放不盖住导航 |
| 离线 | 清缓存断公网后资源仍可加载；失败显示海报而不是黑屏；无远端CDN |
| 真实性 | 模拟、原理、目标装配、实物记录清楚区分；不宣称身份识别/群控/全向避障 |
| 安全隔离 | 展示鼠标、键盘、滚动、动画绝不发送机器人命令；固件回归保持 |
| 发布 | 固定commit、外观资产hash、原始截图/录像、PASS/FAIL/NOT RUN与成套回退 |

PR仍保留“安全任务自身停摆时独立撤销PWM/实体停止未证明”的门槛。本轮外观规格没有关闭这项实物阻断，也未重新运行整套固件或控制机器人。[R1]

## 17｜本包如何使用，以及本轮验证的边界

交给Codex时，先读 `CODEX_NEXT_GOAL.md`，再读本报告和三个资产契约；参考图用 `references/manifest.json` 确认类别及来源，不能把商家图当作已授权网页素材。配置里的null不是错误，而是明确的未知事实。

`starter/story-math.mjs` 是纯数学起点：列主序矩阵/局部方向变换、可逆关键帧、从rest求姿态、正交轮系目标和一次声波往返的参数化。它没有DOM、网络和硬件接口，也没有做出完整渲染。`dark-design-tokens.css` 只作用于新的展示命名空间，不覆盖控制台。

本轮实际执行14项示例回归，14 PASS、0 FAIL；覆盖原姿态不漂移、任意跳转一致、同向锚点变换、轮系限幅和波形归位。另复核了保存CAD导出哈希、隐藏舵机矩阵、11张参考裁剪及6组配色对比度。[E1–E3]

**本轮未完成：完整写实GLB、新官网/全部WebGL验收、原生SolidWorks配合检查、物理线束测量、设备烧录和实物动作。** 不把示例14项通过称为全站通过，也不把本报告中的画面描述称为已经制作的成片。

最终任务是完成可信的产品表达：原设计不用重来，外观不能随意换型，动画不能违背方向，画面不能扩大功能。先把第一段做成立，再把余下内容收成一个可重复的答辩版本。
