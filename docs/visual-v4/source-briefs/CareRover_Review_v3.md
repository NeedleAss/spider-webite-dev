## 01｜本轮判断：分开三个验收口径

### 软件修复：可以确认进步，不能回退

本轮独立边界测试在 SAFE_BASELINE 下为 **17 PASS / 0 FAIL / 1 SKIP**，在 DEMO_BALANCED 下为 **18 PASS / 0 FAIL**。命令到期、所有者断开、人物静默、普通停止取消旋转，以及 IMU 故障保持等被测试路径已关闭。最新 PR 的 GitHub Actions 也已成功，返回的十个任务全部成功，包括九个主控构建任务。[S01–S05；E01–E03]

### 展示产品：尚未达到新要求

现有页面实现了上一阶段约定的悬停展开、选中固定、目录、原理示意和静态降级，但没有连续的滚动分镜、主角切换、部件近景和实物材质层。这部分应明确记为**新的展示验收要求**；不要把一项此前没有实现的滚动叙事说成已完成，只剩换色。[S06–S10]

另一方面，传感器方向和默认背面不是审美偏好：在当前保存装配中，摄像头、超声模块朝外轴为世界 −X，特效却沿世界 +Z，二者相差约 90°。默认相机位于 +X 一侧，确实从错误一面看车。[E04]

### 实物发布：仍不能由软件结果代替

本轮没有烧录、PWM 测量、实体运动或安全任务停摆试验。PR 自己也保留了这项发布阻断：驱动 240 ms 期限由同一个安全任务检查，不能证明该任务自身停止运行后仍能撤销 PWM。已通过的源码测试不能自动转记为实体通过。[S04、S12]

**建议：保留 PR 的软件成果；展示部分按本报告再迭代；最终交付分别记录“源码与构建”“展示与内容”“实物与现场”三个状态，而不是笼统写全部 PASS。**

## 04｜用户指出的方向问题：根因和定量结果

当前 `presentation/app.js` 把 `effects` 加到整个 scene，再将其 position 设置成选中零件的包围盒中心。它没有继承零件姿态，也没有使用镜头中心或换能器表面。视锥、检测框、声波环和障碍平面统一建在自己的 +Z 方向。[S07]

当前精确 GLB 的装配矩阵把两个模块的局部 +Z 都转到世界 −X。以下结果来自原 CAD 重新导出的同哈希资产，不是根据名字猜方向。[E04]

| 项目 | 摄像头 | 超声模块 |
|---|---:|---:|
| 保存几何推导的局部向外轴 | +Z | +Z |
| 转到当前装配世界坐标 | −X | −X |
| 当前原理效果的世界轴 | +Z | +Z |
| 方向偏差 | 约 90° | 约 90° |
| 包围盒中心与候选表面锚点距离 | 约 25.0 mm | 约 15.8 mm |
| 物理标定/实物确认 | NOT RUN | NOT RUN |

原点的偏差是**保存几何层面的比较**，不是声学中心或光学主点的测量精度。候选锚点供改版起步，最终仍应由正面照片和实际安装核对。

摄像头效果显示成一团乱线，有确定的方向、起点和构图原因；代码里没有足以支持“字符编码错误”的证据。不能只改字体、转义或给线条加亮，就说修好了用户所说的“乱码”。

### 必须建立传感器局部坐标架

```text
robotModel（保留统一的单位转换）
└─ camera-1（保留原装配 TRS 与拆解位移）
   ├─ cameraAppearance（真实外观，不承担坐标裁决）
   └─ cameraAnchor（镜头表面、局部朝前轴）
      └─ cameraEffect（视域、虚拟目标、检测示意）
```

超声模块同理。这样整车旋转、部件拆解、单独近景时，效果始终跟随安装方向。Three.js 的父子变换负责继承局部姿态；不能只复制位置而遗漏旋转和比例。[W03]

`SENSOR_ANCHORS_CANDIDATE.json` 给出本资产的几何候选：camera 局部 `[-0.011, 0, 0.0204] m`，ultrasonic 局部 `[0, 0, 0.0133] m`，局部向外轴均为 `[0,0,1]`。实际视场角、波束角、TX/RX 身份仍为 null，禁止自行填成“已标定”。

**单位陷阱：** 当前 viewer 将 GLB 根放大 1000 倍，世界渲染量级近似毫米；零件局部位置仍以米保存。把效果改成零件子节点后，原来的 65 个世界单位应是约 0.065 m 的局部示意长度，不是直接把 65 填进子节点。不要混淆 CAD 世界 +Y 向上、IMU 安装 +X 竖直以及命令 vx 的定义。[S07；E04]

## 05｜首屏必须先看到机器的“脸”

当前 reset 为相机 `[290,185,340]`、目标 `[0,44,0]`，即从 +X 一侧观察；实际传感器面朝 −X。正确方法不是给整车随机转一个角度，直到某台显示器上似乎顺眼，而是固定 `front/up/right` 基准，再由这个基准生成镜头。[S07；E04]

![原始方向与候选方向的几何诊断](evidence/orientation-comparison.png)

*图：同一真实 GLB 的 VTK 离屏几何诊断；左为当前默认方向，右为候选正面方向。不是原网站 WebGL 截图，不是最终材质或视觉成稿。*

建议第一镜头以传感器面为主，偏航约 15–25°、略有俯视，让双超声圆筒、镜头、外壳轮廓和轮组都可辨。这个角度范围是美术起点，不是机械标定值。若侧面屏幕遮住传感器，宁可减少侧面面积，也不牺牲用户指定的正面。

初次加载先给完整机身一个稳定的观看机会，不因鼠标已经位于画面中央就立即炸开。完整、拆解、部件近景都要以相机目标与包围盒适配画幅；选中镜头时，不能仍受整机 `minDistance=250` 的固定限制而只看到远处小零件。[S07]

首屏静态 poster、WebGL 完整状态和结尾实物照片必须选择同一面。原 `assembly.png` 是保存的 CAD 预览，不能继续拿它当与新主镜头相反的降级海报。海报的模型包围盒应有足够画幅占比，而不是图片容器很大、真正机器人只有一小块。

## 07｜直接看苹果，应该借鉴什么

本轮查看的 iPhone Air 页面把整机形态、局部近看、内部设计、相机能力和使用结果分成不同段落；MacBook Pro 页面同样以产品画面与分主题内容推进，而不是一开始把全部参数和全部操作面板摊开。[W01–W02]

对 CareRover 的设计推导是：**每一屏只让一个重点成为主角，画面变化必须解释它，文字再补充观众需要理解的那一层。** 这不是要求照搬苹果文案、字体文件、图标、产品素材或网页代码。

| 当前做法 | 下一轮建议 |
|---|---|
| 标题、模型、侧栏、目录同时竞争 | 首屏先认识机器人；进入对应章节才出现该章节说明 |
| 所有零件同时等速散开 | 外壳打开→内部关系显露→重点模块浮出，分清先后 |
| 绿色线条本身就是“动画” | 每种效果展示一个因果：目标进入→被检测；声波返回→得到距离 |
| 一套材质套到所有部件 | 白色打印件、橡胶、PCB、金属、玻璃各有自身的表面反应 |
| 观众必须自己转到对的位置 | 默认镜头已选好；自由旋转仅作为主动进入的探索模式 |
| 把安全/来源声明全塞进主视觉 | 主画面保留必要状态，技术边界和版本放在紧邻说明或技术页 |

所谓高级感，不应等同于“所有字更小、所有东西更白、所有界面都透明”。对这个项目，材质细节、光照轮廓、前后景关系、文字留白和正确的镜头，比增加十个装饰动画更有效。这是本报告的设计判断，不是苹果的工程规范。

**技术路线不倒推。** 漂亮的官网素材可能由多种制作方式组成；本轮没有证据确认苹果特定段落的渲染栈。因此不建议为了“像苹果”改成新框架、引入多套动画库，或要求全页实时物理渲染。保留本地 Three.js 0.180.0 和现有原生模块即可实现需要的分镜。

## 08｜建议的完整页面：七章，而不是十五张部件卡

这是下一轮的分镜规格，不是已实现状态。建议总体验控制在约 90–150 秒的讲解内；普通用户可以更快滚过、直接跳章或回看。七章顺序可在资源不足时合并，不能删掉第一章正面或关键方向修正。

### 第一章：认识 CareRover

**画面：** 完整机器人，摄像头与超声波面朝观众，偏斜很小；白色机身与背景有清晰边缘，轮子接地。画面中不自动展开，不漂浮乱转。

**文字建议：** “CareRover。把感知，变成行动。”下面只补一句“我们设计并制造的移动健康机器人”。这类产品句是建议文案，不能添加未实现的承诺。

**交互：** 下方一个明确的“向下探索”；小型章节导航；“结构探索”作为次入口。主模型占可用视觉区域的大部分，不把几百像素空白叫留白。

### 第二章：打开机身，看到秩序

**画面：** 先抬起顶盖，再移开外壳；底盘与电子模块保持参考位置。镜头只轻微上移，观众能追踪刚才的整机与里面的关系。

**文字建议：** “打开外壳，看到协作。”最多三组标签：感知、主控、驱动。线束在结构模式中可略简化，但其存在和连接方向不能消失。

**禁止：** 十五类部件一次飞到四面八方，或直接把整个机器人缩成一粒点，为所有标签让路。

### 第三章：摄像头——先看见，才跟随

**画面：** 相机模块从装配位置稍微向前突出，镜头放大，外部结构退为安静背景；局部视域从镜头朝前延展。虚拟目标进入同一视域，在对应图像平面出现一个整齐的检测框，再出现“人脸位置 / 手势结果”的短说明。

**文字建议：** “看见目标，也看懂手势。”补充“提供检测结果，不进行身份识别”。目标丢失时，框消失或转成明确失效状态，不用不停闪烁的字符雨表现 AI。

**因果顺序：** 目标进入→检测→位置/标签→交给主控。摄像头不是激光雷达；视域是解释画面范围的示意，不是相机真的向外发光。

### 第四章：超声模块——回声成为距离

**画面：** 双换能器的金属端面可见。沿其正前方放一个简单障碍；一次波前从已确认的发射端向外，碰到障碍后，回波返回接收端。若尚未确认 TX/RX 标记，用模块整体的往返示意，不乱指定左右。

**文字建议：** “一次回声，多一份前方判断。”补充“前方测距与有限场景保护”。距离公式可以在技术说明出现，但不把示意速度/夸张时长写成实测声速。

**绕障：** 第二阶段可切俯视小动画，按现有固定向右单障碍逻辑解释；明确它不是全向感知，不承诺检测侧后方。未完成实物验收时只保留示意标签。

### 第五章：主控——让有效信息成为决定

**画面：** 主板外观真实，去掉两条假结构块。短数据路径分别从相机、IMU、超声和健康模块进入主控，再从裁决区域流向执行器；端点绑定真实部件，而不是三个任意方向的光点。

**文字建议：** “不是收到指令，就一直运动。”展示一条最有解释力的对照：有新输入→输出；输入失效→归零。用简洁的“有效 / 等待 / 停止”状态讲工程，而不是把所有内部日志放进画面。

### 第六章：真实轮组，真实反馈

**画面：** 先给全向轮与舵机近景，展示实际轮型和连接；再给屏幕或健康传感器一个干净的插入镜头。不要把未知滚子结构画成普通轮胎或麦克纳姆轮，不发明编码器反馈。

**文字建议：** “结构配合，才有行动。”副说明分别解释开环归一化目标和接触式健康原型。健康曲线标“原理示意”；真实结果必须来自明确标识的实机/历史数据。

### 第七章：重新组成你们的机器人

**画面：** 按第二章的相反路径精准收拢，回到第一章镜头；随后可淡入一张同角度的真实整机照片。模型与实物的轮廓对得上，是最有说服力的收尾。

**文字建议：** “从设计，到真实运转。”提供“自由探索结构”“查看已验收演示”“技术与版本”。进入控制台是明确的页面切换，不让展示滚动事件变成运动输入。

## 09｜滚动运行时：一个进度源，一套可逆姿态

建议默认使用原生文档滚动，不拦截整个页面的 wheel 去执行 `preventDefault()`，也不强制锁死滚动吸附。章节提供 PageDown/PageUp 或显式上一章/下一章入口，使演讲者能像翻 slide 一样操作，但鼠标、触摸和键盘仍能自然退出。

用单个 sticky 画布配合 DOM 章节：章节内容存在于文档中，3D 按当前章节进度取姿态；无 WebGL 时仍能读到所有文字和对应 poster。默认滚动期间不运行 OrbitControls 的旋转/缩放输入。OrbitControls 的滚轮缩放是现有查看器的一部分，直接叠加滚动叙事会竞争同一个手势。[W04]

建议只有两个用户模式：`STORY` 与 `INSPECT`。STORY 的镜头由章节决定、画布不截获垂直滚动；INSPECT 由用户显式进入，才启用拖动/缩放。退出 INSPECT 回到先前章节及进度，不把整个页面跳回顶部。

### 建议的模块边界

```text
presentation/
  app.js                 生命周期、Story/Inspect 切换
  story/chapters.js       每章文字、关键帧、强调对象、来源标签
  story/timeline.js       根据 progress 计算唯一场景状态
  scene/robot.js         rest pose、部件/实例、外观层
  scene/anchors.js       相机/超声/连接端点
  scene/effects.js        仅示意效果；不 import 运动 Transport
  scene/render-loop.js   按需绘制、resize、可见性与上下文故障
  assets/...             自有模型、贴图、poster、本地库
```

这只是职责分离，不需要为了文件数建立大型框架。现有 parts.js 中的功能文案可迁移复用，原 GLB 留作不可变的几何基线。

### 姿态不能依赖“滚动触发了多少次”

给每个章节定义起止状态。章节 progress 从文档布局算出，限制在 0–1；位置 lerp、旋转 quaternion slerp、光照和强调从同一进度求值。每次都从保存的 rest pose/关键帧算目标，禁止在当前节点上反复累加位移。

整体应满足：同一 progress，无论往上滚还是往下滚、快滚还是慢滚，得到相同最终场景。短暂跟随平滑只作用于展示值，不能不断推进时间而使停下后的章内容继续飞走。首次加载到 URL 中段、窗口尺寸改变和浏览器历史恢复都需要重算布局。

每章可采用“前 20% 过渡、后 80% 阅读与展示”的起始节奏，按真实版面调整。镜头完成后应让观众有时间读文字。不要在阅读中同时切材质、飞多个部件和播放三种循环特效。

## 10｜真实感：保留 CAD 布局，增加实物外观层

当前 GLB 为 701,560 字节，15 类网格、20 个可见实例、15,110 个唯一网格三角形；纹理、图片和 UV primitive 都为零。每类只有一个统一展示材质，金属度均为 0.12、粗糙度均为 0.5。它保留了布局信息，不具备完整的实物表面描述。[S09；E04]

**最适合这次项目的路线是混合制作：CAD 负责位置与装配关系；实物参考负责外形细节和材质；线束单独制作；必要的照片/预渲染负责极近景和备用展示。** 这比临交付对整车做一次扫描，再期待自动得到所有独立零件，更可控。

建议在衍生展示资产中分开三个层：

```text
engineering_source  原始 CAD / 本轮精确导出：只读，保存来源
assembly_rig        实例 ID、rest transform、锚点、章节位移
appearance          实物网格、UV/贴图、连接器、柔性线束
```

修改外观不能改变装配基准，更不能回写到固件的轴、引脚、NVS 或控制协议。换一块更真实的板，必须仍绑定原来的部件 ID、安装位置和连接说明。

| 部件 | 最有价值的真实感补充 | 不该做的替代 |
|---|---|---|
| 白色打印外壳 | 实际厚度、开口、倒角；轻微粗糙和适量层纹；正确白平衡 | 强行做成镜面金属或满身发光 |
| 全向轮 | 核对型号、滚子数/方向、轮毂和橡胶表面 | 普通圆柱仅涂黑就称实物轮组 |
| 舵机 | 实际壳体、连接耳、输出轴、线出口、标签 | 未知型号的通用高精模型 |
| 主板/传感器板 | 丝印、芯片、排针、USB/连接器、大电容等可见轮廓 | 整块单一绿色、把杜邦线代理当板下支架 |
| 摄像头 | 镜头层次、黑色镜筒、板边与支架、微弱玻璃反射 | 向错误方向射光束 |
| 超声模块 | 两个端面、金属外圈、黑色网罩、PCB 与引脚 | 两个绿色实心圆柱 |
| 电池/屏幕 | 真实包覆与安装方式、屏幕边框及现有 UI 内容 | 虚构电量采样、虚构动态数据 |

PBR 工作流中，材质、环境反射与表面细节共同影响结果；Three.js 的标准材质文档也建议配合环境图获得更好的物理材质效果。[W05] 本项目应使用有授权、本地保存的柔和棚拍环境或自建灯光，配合接触阴影，让白色边缘与黑色轮子不丢层次。不要直接增大曝光把所有材质冲成同一种灰白。

颜色贴图与数据贴图需要正确的色彩空间；不能把 normal/roughness 当作普通彩色照片处理。先让轮廓和材料反应正确，再细化微小 PCB 文字。手机上看不到的极微小细节，不值得占据大量纹理和制作时间。[W05]

## 11｜照片、扫描、厂商模型：分别能解决什么

用户提供照片非常有帮助，但不同资料解决的问题不同。整机照用于核对外形、正面、可见部件与装配版本；部件近照用于外观材质和关键几何；尺寸用于比例；接线照用于线束端点。仅有一张正面照不能重建所有隐藏面和内部拓扑。

### 本次推荐顺序

先取得实际型号和几张关键参考。已有匹配型号、授权清楚的厂商网格可作为外观起点，但必须核对尺寸、连接器方向和版本，不能凭“长得差不多”替换。

再用原 CAD 结构补关键外形：轮子的滚子、镜筒、超声端面、板上大件和线束。这些直接改变近景轮廓，比全板每个电阻都做几何更有效。板面丝印可用校正后的自有照片制作贴图，但要避免把强灯光阴影烘进颜色，造成转动后阴影跟着表面走。

扫描作为可选项，不应成为两天交付的唯一依赖。Apple Object Capture 的官方说明指出：刚性、纹理丰富、漫反射表面更合适；透明、反光和缺乏纹理的区域会更困难。[W06] 你们的白色外壳、金属换能器、镜片和细线，恰好需要额外清理和人工判断。

即使全车扫描成功，扫描表面也不会自动给出隐藏主板、每根线连接哪一个引脚，或可动画拆解的 CAD 装配树。因此更适合“整机真实参考/外观校验”，而不是直接替代部件绑定系统。这是根据任务所需语义与扫描输出做出的工程判断。

### 最低资料包与可选完整资料包

| 资料 | 本次最低要求 | 有余量再补 |
|---|---|---|
| 整机外观 | 正面、背面、左右侧、顶部；至少一张前侧 3/4 照 | 同一灯光下完整一圈与不同高度的重叠照片 |
| 关键近景 | 镜头/超声、一个轮子、一个舵机、主板正面 | 各模块背面和连接器；型号清晰照片 |
| 内部排布 | 断电状态下现有可安全打开的内部照片 | 多角度线束和固定点 |
| 尺寸 | 整机外形、轮径、板尺寸，带尺参考即可 | 孔距、支架、镜头/换能器突出量 |
| 线束 | 两条矩形代理对应的实际线、两端连接到哪里 | 中间走线、固定点、颜色与插头形式 |
| 实物一致性 | 第四舵机是否存在且可见；显示窗口和传感器面确认 | 最终装配与 CAD 配置差异表 |

拍摄建议是本项目的素材制作要求：均匀柔光、干净背景、焦点清晰、避免人像虚化和重度滤镜；尽量固定白平衡/曝光。不要为了拍底面冒险翻转带电机器，不要求拆除不明接线。现场人员先断开动力并确认安全，不能让摄影需求触发运动或重新接线风险。

未提供部分可以制作明确标注的简化外观，但不能称“完全扫描级复刻”。原始照片保留私有版本；对外展示副本检查人脸、Wi-Fi 口令、设备备份、个人信息和授权。

## 12｜那两条长方形：应当做成线束，不是删掉主板

用户明确说明它们是建模时用于模拟杜邦线的代理块。当前导出器将每类零件的保存网格合为一个 mesh primitive，主板网格未提供能直接按名称开关的“wire”子节点。因此在网页里简单 `getObjectByName('wire').visible=false` 不是可靠修复。[S09；E04；用户本轮说明]

最佳做法是在衍生外观资产中分出已确认的代理几何：若原 CAD 中能按实体/特征识别，单独导出；若不能，由建模者在 Blender/CAD 中确认后分离。保存原网格和替换记录。**不允许通过删除“主板下面所有三角形”来蒙混过关**，因为连接器、真实支架可能同时位于该区域。

真实线束使用少量柔和曲线加圆形截面，必要时补杜邦接头和排针。端点锚在真实连接器，曲线路径服从装配空间，不能悬浮穿壳。没有资料时，用清楚标注的简化线束表示大路径，不猜具体 GPIO 或颜色语义。

拆解时有两种合理表现：用于介绍结构关系的章节可淡出部分线束并说明是展示省略；用于连接讲解的章节让两端随部件移动，并重算中间控制点。不能把柔性线当无限拉长的直杆，也不能把连接线直接拉穿 PCB。

建议在主剧情只突出两三条正在讲解的数据/供电路径，其余线束保留较低视觉权重。功能强调可以减少干扰，但在最终完整机身与实物对照时应恢复真实外观。

## 13｜版面、材质与镜头的验收规格

以下是建议的制作目标，不是苹果标准，也不是本轮测得的最终性能。

**首页比例。** 桌面以一块主舞台为中心，标题和模型不各占一半又互相让位。完整机身的可见高度可从可用舞台的 65–75% 起步；镜头近景要让被讲解部件成为画面的绝对重点，不能仍是全车旁边一小块。边界要容纳顶部盖板、四轮和接触阴影。

**文字。** 重要正文从 16–18 px 起步，辅助正文不低于可舒适阅读的 13–14 px；不再用 9–11 px 承担核心说明。大标题服务章节主张，而不是整页每张卡都使用大标题。中文留足行高和有限行长；投影屏应单独检查。

**颜色和灯光。** 外壳白不等于背景必须纯白。可以用略暖浅灰的整机章节、较深石墨的电子近景章节，但不要每屏换一种主题。强调色只标当前数据/选中对象；真实 PCB、金属、橡胶和玻璃保留各自颜色，不在选择时一起染绿。

**标签。** 同时最多呈现当前叙事需要的两三个标签，端点跟随三维锚点、文字留在清晰的 DOM 区域。使用遮挡/投影位置判断，避免标注线穿过屏幕文字；不可见部件的标签不应该指向一团透明网格。

**运动。** 有阅读停顿，有首尾呼应，能反向滚动。镜头路线不穿透机壳、不过度旋转，不让观众为理解一个传感器绕车一圈。关闭动态效果后内容仍完整，章节切换可以使用静态画面或短淡入，不依赖连续飞行动画。[W07]

**目录。** 保留十五类部件作为二级探索入口，而不是首页的主体结构。目录里的预览也应从最终外观资产统一生成，不混用带 CAD 紫灰面、工程边线和不同角度的历史缩略图。

## 14｜移动端与降级：本轮已经抓到一个真实缺陷

原样静态分支在 1280×720 和 390×844 的内存资源测试中，没有横向溢出；十五个目录按钮存在，选择相机和 Escape 清除工作正常。但 stage 计算样式始终为 `touch-action:none`，即使 WebGL 已不可用、只有一张静态图。[E05]

在模拟触摸测试中，同一上滑手势从模型区域开始时 `scrollY=0`，从页边开始时可以翻页。用户会感到中间那块大区域“滑不动”。这不是还需讨论的审美问题。

本包附一个最小候选补丁：

```css
/* 静态降级没有 3D 手势需要独占，应恢复页面垂直滚动。 */
body[data-viewer='fallback'] .stage { touch-action: pan-y; }
```

只修改本地候选副本后重新测试，模型区域的同类上滑产生了 `scrollY=225`；选择、Escape、无横向溢出等对照仍通过。该数字是一次测试结果，不是所有设备应滚动的固定距离。补丁未提交远端；它只解决静态分支，不替代新 Story 模式的手势设计。[E06]

![原静态降级桌面首屏](evidence/static-desktop-viewport.png)

*图：经过资源内联的原静态分支浏览器截图，非 WebGL。标题、侧栏、按钮和保存预览的位置来自当前代码。*

新版本应测试 360/390 px 手机、手机横屏、平板和 1366×768 笔记本；验证从画布、文字、按钮、页边开始的拖动、滚动与键盘操作。不要把“无横向溢出”当成手机体验全部通过。

降级不仅是显示一张小图。每个主要章节需要与其对应的清晰 poster；无 WebGL、模型载入失败、低动态偏好仍可以读完整个故事。上下文丢失不应无条件 reload 到第一屏；恢复当前章节，或者保持静态继续讲解。[S07]

## 15｜性能与工程组织：不为美术引入新的失效链

保留独立电脑端展示。它不 import 控制台运动 Transport，不建立机器人 WebSocket，不进入 ESP32 FFat 包。通过明确入口打开控制台时，也不把展示页的键盘监听带入控制台。这个隔离是 PR 已经做对的部分，应继续保留。[S06、S12]

当前原始网格只有约 1.74 万个实例化三角形，不是模型三角形过多导致“建模感”的证据。先补关键外观、材质和照明，再依据目标机器分析开销。文件小不代表所有循环绘制都合理；增加纹理后还要分别记录下载体积、解码后内存和 GPU 资源。[E04]

建议给默认展示制定总资源预算，例如首批可见资源争取 5 MB 左右、其余近景按章节懒加载；桌面动画以 60 FPS 为目标，移动端提供 30 FPS/较低 DPR 档。这些是起始工程预算，不是已测成绩，也不是统一浏览器上限。

静态状态停止绘制；滚动过渡、相机阻尼和当前章节效果活动时才持续渲染。隐藏页和离屏区域暂停；缓存包围盒、材质和锚点，避免每帧 new Box3/Vector3、重建整套效果。当前每帧计算投影矩阵、持续 rAF、以及全网格透明化都应在改版时收敛。[S07]

资源需本地化且锁版本；先不增加 Draco、KTX2、多个解码器和新构建平台。确有体积压力再引入一种可测的压缩方案，连同解码器离线验收。供应商资产保留许可；字体用系统回退或有明确授权的自有选择，不拷贝苹果字体文件。

## 16｜控制台与实物：仍需处理的收尾问题

### 急停显示应反映确认层级

现有 emergency 在设置本地 latch 后调用 send，但没有把发送失败写入单独状态；随后提示“紧急停止·控制已锁定”，页面又显示“急停已锁定”。本地输入及时锁定是对的，但应明确三个可观察状态：本地已锁定；请求已发送/未送达/等待确认；设备上报急停。没有实体测量时不显示“车已物理静止”。[S11]

修复不应等待发送成功才锁输入，也不应让超时自动解锁。断网急停后保持本地锁，并告诉操作者设备未确认、使用现场实体停止手段。恢复仍须遵循原来的 ACK 和设备状态条件。

### 回放与时间轴

当前标题计算先判断 stale，再判断 replay。回放主动断开实时 Transport，`isTelemetryStale()` 又将非连接态视作 stale，因此“会话回放”标题分支被前面的等待连接分支覆盖。调整显示优先级，测试回放开始、暂停/结束、返回实时和真实断线；不能借此放开回放期的指令发送。[S11]

PPG 批次被传入 Date.now()，而不是采用定义清楚的源批次时刻。短期可以保留可用波形，但应修正文档、显示断批缺口和录制/回放时间映射；不要在这轮同时重写整个健康算法。保持值、原型非医疗用途和无手指空值继续保留。

### 物理发布仍需单独放行

同一设备、同一主控/CAM/Web/配置和校准版本下，架空验证：持续 ping 但停 cmd_vel、只断 WS、人物 P 静默而 G/IMU 继续、普通停止后继续 yaw、IMU 缺失/倾倒恢复、前方保护各阶段失效。每项区分 target 归零、PWM 中位和实体停止。

安全任务自身冻结时，应独立测得 PWM 与车轮行为；仅看到软件中存在 240 ms 变量不能关闭该项。未知时保持受限、有人监督且可断动力的验证条件；未达到运动放行要求，就使用 observe、明确标识的模拟或历史录像展示，不伪装实时实物。[S12]

公开文档删除口令并不证明现场口令已经轮换；只需记录“轮换已确认/未确认”，不要在新报告或截图里再次写出口令。不要为了最后交付未经协调重写 Git 历史。

## 18｜两天内的实施顺序与停止扩张规则

**第一条线：固件与现场。** 保留当前修复，通过原项目完整测试与构建后，进入固定版本现场检查。除复现到的关键缺陷外，不再改识别算法、IMU 轴或控制框架。

**第二条线：展示。** 第一个 3–4 小时先交“真实正面首屏→外壳打开→摄像头近景”这一段，不做七章空壳。由用户看图确认方向、机身比例、真实材质目标和文字节奏，再扩到超声与主控。

**第三条线：资产与证据。** 尽快收集正面/关键模块/线束照片，确认第四舵机和最终外壳版本；为缺失资产选择明确替代路线，而不是等待完美扫描。

| 相对时间 | 可交付结果 | 不应再扩大的内容 |
|---|---|---|
| T0–4 h | 正面、锚点、静态触摸修复；前三镜头可运行；照片收集 | 新框架、新固件功能、未知厂商资产大规模导入 |
| T+4–12 h | 相机与超声完整因果动画；核心外观和线束；章节切换 | 为每个螺丝做剧情、整车高成本扫描平台 |
| T+12–24 h | 主控/轮组/收拢；手机/低动态/离线；阶段视觉验收 | 同时重做所有健康和视觉算法 |
| T+24–36 h | 同版本集成、现场许可范围内复验、性能与文字小修 | 增加新的交互模式和渲染依赖 |
| T+36–48 h | 两次完整彩排、备份录像/静态版、最终冻结 | 未测试的“最后一个效果”、临场随意调安全阈值 |

资产缺少时，优先保证首屏、相机/超声近景与真实照片对照；其余部件可以保留明确的简化表示。大规模重建未完成时，采用高质量真实 CAD 衍生渲染/自有实物照片作为章节画面，而不是用通用 AI 机器人替代。

提交可继续在 PR #1 上追加小而清晰的提交，分别为方向与静态触摸、外观资产、Story 运行时、视觉验收与文档。无需为了 PR 数量重新折腾分支，但不要将固件准入调整与美术更换写进一个无法解释的大提交。

## 19｜最终评价与下一步准入

本轮 PR 不是“没有成果”。它把上一轮多个真实运动边界落实为生产逻辑，提供独立回归和构建记录，且已经导出了与原 CAD 保存装配一致的可用 GLB。应当保留这些基础，尤其不能为了演示更顺滑再删除失效归零机制。

但**“真实 CAD 来源”不等于“真实实物外观”；“有悬停拆解”不等于“产品级滚动叙事”；“示意动画”不等于可以忽略传感器朝向。** 当前展示不能按用户新目标验收为最终稿。

下一步的成功标准不是加更多效果，而是完成一条完整链：**正确的正面 → 有秩序地打开 → 看清真正部件 → 看懂它的方向和作用 → 精确合回 → 与实体照片一致。** 同时，控制台对真实状态负责，运动发布由真实证据负责。

本报告附带的 Codex 文件要求先做这条链最前面的几段并给出关键帧，避免再交一份“所有卡片都有了，但没有一屏真正成立”的版本。
